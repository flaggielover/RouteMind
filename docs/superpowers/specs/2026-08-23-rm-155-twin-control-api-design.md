# RM-155 Digital Twin Control API Design

Date: 2026-08-23

## Goal

Expose bounded, deterministic controls for the existing Python-owned
`ScenarioKernel`: start, pause, resume, step, reset, speed, scenario, seed, and
strategy. Responses must make simulated time, emitted events, and replay
provenance explicit. The control surface is simulation state, not durable
business state.

## Options considered

1. Add a new simulation service. This would isolate runtime failures but adds a
   deployment and synchronization boundary without a demonstrated scaling need.
2. Put mutable controls in FastAPI route globals. This is small, but couples
   validation, replay hashing, and command deduplication to HTTP handlers.
3. Keep a process-local `TwinControlService` around the existing kernel and
   expose thin FastAPI adapters. This preserves the Java/Python ownership split,
   keeps the kernel framework-free, and makes control semantics directly
   testable. This is the selected approach.

## Design

- `TwinControlService` owns one bounded in-memory session. It validates a
  scenario id, non-negative seed, registered strategy, speed in `[0.1, 10]`,
  and step seconds in `[1, 3600]`.
- A command has a caller-supplied `command_id`. The service stores only a
  bounded recent idempotency window. Repeating the same id and payload returns
  the original response; reusing an id with a different payload is rejected.
- `start`/`resume` set `running`, `pause` sets `paused`, `step` advances only
  simulated time (scaled by the current speed), `reset` clears progress, and
  `speed` changes the playback multiplier without changing progress. Scenario,
  seed, and strategy changes reconfigure and reset the session. Commands never
  derive simulated time from wall-clock time.
- Each response returns the full state plus newly emitted events. State and
  event canonical JSON are hashed into a replay digest. Scenario decisions are
  generated by `ScenarioKernel` from a deterministic manifest factory; no
  external provider or durable store is required.
- `GET /api/v1/twin/state` is read-only. `POST /api/v1/twin/control` accepts the
  command envelope and returns a control response. Invalid commands return
  422, unknown strategies return 400, and idempotency conflicts return 409.

## Verification

Focused tests cover every command, bounds, state transitions, simulated-time
separation, deterministic replay, duplicate command replay, idempotency
conflicts, unknown strategies, and API error/status mapping. The existing full
Java/Python/Web/contract gates remain required before the remote Evidence Gate.
